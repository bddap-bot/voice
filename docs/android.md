# Live Voice on Android

[Install Live Voice](https://github.com/bddap-bot/voice/releases/download/android-v6/live-voice.apk) (Android 9 or newer). The app loads the same [Live page](https://bddap-bot.github.io/voice/) as the browser. Conversation logic, authentication, wake detection, speaker filtering and replies remain in that page; the app keeps that page running and hearing while it is hidden.

Tap the APK link → Download → Open → Settings → Allow from this source → Back → Install → Open. Version 6 installs over versions 2, 3, 4 and 5 and preserves the connection token. Version 1 used a different signing key and must be uninstalled first. Open the app, allow microphone access while using the app, and allow notifications. Re-enroll with **Learn my voice** if you want voice filtering; the saved browser voiceprint does not transfer. Browser storage does not transfer to the app. You can turn off “Allow from this source” after installation.

Swiping Live Voice away from Recents ends background capture. Before a page session starts, the notification’s mute action does nothing. An OS-killed process does not silently restart capture.

## Diagnosis: Android silences the microphone, the page cannot see it

Android grants microphone access to an app only while it is visible or while it runs a foreground service of [type `microphone`](https://developer.android.com/develop/background-work/services/fgs/service-types#microphone). When an app loses that capability, Android does not end or mute the capture: it keeps the recording running and feeds it silence. The Android audio service reports this as `silenced:true` on the app's recording (`adb shell dumpsys audio`, `RecordActivityMonitor`).

An experiment on an Android 15 emulator shows it. The same app built with its foreground service declared only as `mediaPlayback` kept a `live`, unmuted WebRTC track, advancing capture counters and a connected peer after Home and after screen-off. In both hidden intervals, though, Android reported that recording as `silenced:true`. The page sees a healthy microphone that hears nothing: listening stops a second or two after switching apps, with no error. A web page cannot request a microphone foreground service for itself, so it cannot keep this capability once hidden.

The app holds the capability. `VoiceService` starts as a `microphone|mediaPlayback` foreground service while the activity is visible and after microphone permission ([background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start) forbid starting it invisibly). The service, not the visible screen, owns the WebView, so Home and screen lock do not end the page. Task removal calls the same shutdown method as notification Close. It asks Android to treat the WebView's renderer as important so it is not killed while hidden, holds a partial wake lock, and never calls WebView `onPause` or `pauseTimers`. WebView still owns media capture; there is no second native conversation client.

Below that, the page's own path is `getUserMedia` → optional speaker AudioWorklet gate → `RTCPeerConnection` → model, with replies returning through `LivePlayback` to the speaker element. Hiding the page pauses only puppet rendering. `audio-diagnostics.js` records microphone mute/end, AudioContext states, peer and relay transitions, RTP counters, and page freeze/resume/discard locally (newest 300 records, no audio, transcript, credential or address). The app adds no controls or panels over the page. Diagnostics remain in the page’s local storage for development inspection. Because OS silencing leaves every one of those signals healthy, a hidden conversation whose status looks healthy but hears nothing points to Android's microphone capability, not the page.

OEM battery policies, microphone privacy toggles, calls or other apps taking audio focus, network loss and force-stop can still interrupt a session.

## Build and verification

Install JDK 17 or newer, Android SDK platform 35, build-tools 35.0.0 and zip. Set `ANDROID_HOME`, `VOICE_KEYSTORE` and `VOICE_STORE_PASSWORD`, then run `bash android/build.sh`. The result is `android/build/live-voice.apk`. `bash android/build.sh --test` builds `live-voice-test.apk`, identical except for the debuggable flag, which turns on WebView remote debugging for the runtime test. It is signed with a throwaway key generated per build, so it cannot install over a released copy; install it only on a test emulator. Keep the signing key private and reuse it for updates. The APK contains no connection token and does not permit cleartext HTTP, file access, backups or navigation to other pages. Audio capture is granted only to the deployed HTTPS origin while the top-level page is Live, and its only JavaScript-to-native callback mirrors the page mute button into the notification action label.

`node android/test/background.mjs` drives an Android emulator (`ANDROID_SERIAL`, default `emulator-5646`) through adb. It installs the test build, opens the app, and in the Live WebView runs real `getUserMedia` capture over WebRTC with a synthetic reply tone through the deployed `LivePlayback`. It sets Android to destroy activities as soon as they leave the screen, then samples three 30-second intervals: visible (the control), after Home, and after Android confirms the display is off and the device is in forced deep Doze. Each sample requires a live, unmuted track, a connected peer, a running playback context, nonzero reply audio, and an active, unsilenced `voice.live` recording in Android's audio service. The hidden intervals must advance capture, RTP and playback at least a quarter as fast as the visible control does. The control is used instead of fixed amounts because an emulator on a loaded host runs audio slower than real time even when visible. A stall a second or two into a 30-second interval yields under a tenth of the control rate, well below that threshold. The visible control must itself capture at least a quarter of real time. It then starts the deployed page’s session and microphone through a test-only function appended to its module via DevTools, without a relay or changes to the mute handler. Both notification taps and in-page button taps must change the real capture track and notification label through Mute → Unmute → Mute. The native host observes the page button’s existing aria-pressed attribute; the page remains the only mute state. Disabling the notification label update must make this assertion fail; restoring it must pass. After restoring normal activity handling, it swipes the task away from Recents and requires the service, active recording and running microphone app-op and System UI microphone indicator to disappear. Set `VOICE_ANDROID_STOP_ACTION=notification` to exercise notification Close instead. Screenshots and before/after dumpsys evidence are saved beside `VOICE_ANDROID_EVIDENCE` (default `android/build/background-evidence.json`). Removing `VoiceService.onTaskRemoved` must make the swipe test fail; restoring it must pass.

The test drives the app through adb input only, because an attached instrumentation exempts the app from Android's background microphone restriction.

Run `npm test`, `npm run build` and `npm run smoke:ci` for the page. The emulator cannot prove physical speaker output, a real model reply, OEM power management, Bluetooth routing or long idle periods; those remain checks on the phone.

`node android/test/appearance.mjs` checks native HTML select dialogs with neutral choices, their change event and storage, activity destruction/recreation, and process restart. Run it against an installed app with WebView debugging enabled; `ANDROID_HOME` and `ANDROID_SERIAL` choose the SDK and emulator. `VOICE_ANDROID_EVIDENCE_DIR` chooses the evidence directory. On a rooted test emulator, `VOICE_ANDROID_DEBUG_HELPER` may name an executable that enables inspection of an unchanged release APK before each connection. The test replaces the page body with its fixture; real appearance rendering and server-side selection persistence are separate checks on the published page.

Version 6 supplies the current activity context to the service-owned WebView while attached, and releases that activity on detach. Native appearance dialogs can then open without changing the background capture lifecycle.
